# Совместное редактирование (VectorCraft Cloud)

Несколько человек работают в одном документе одновременно, как в Figma. Правки видны всем в
пределах кадра, ничего не блокируется, одновременные правки сливаются. Каждый видит курсоры и
выделения остальных.

## Как это устроено

```
 ┌──────────────┐   Yjs sync + awareness    ┌─────────────────────────────┐
 │ VectorCraft  │ ◀── WebSocket (binary) ──▶ │ vectorcraft-collab-server   │
 │ (desktop/web)│   ws://host/collab/<room>  │  комнаты · ретрансляция ·   │
 └──────────────┘                            │  хранение <room>.ydoc       │
        ▲                                     └─────────────────────────────┘
        │ каждый кадр: Collab::tick
 ┌──────┴───────────────────────────────────────────────────────────────┐
 │ engine::collab::Collab    публикует свои правки, применяет чужие,     │
 │                           выполняет Undo/Redo через общую историю     │
 │ collab::SharedDoc         Document ⇄ CRDT (yrs, совместим с Yjs)      │
 │ collab::Connection        протокол синхронизации и присутствия        │
 └──────────────────────────────────────────────────────────────────────┘
```

Все правки в VectorCraft выполняются командами (`Session::execute`), а документ — это неизменяемое
дерево `Arc<Node>`, которое при каждой правке заменяется новой версией со структурным разделением.
Поэтому совместному режиму не нужны изменения в командах, инструментах, MCP и протоколе
управления: слой синхронизации смотрит, как изменился документ.

### Документ в CRDT (`crates/collab/src/mirror.rs`)

Три корневые карты Yjs:

| Карта | Ключ | Значение |
|---|---|---|
| `nodes` | id объекта | карта `{p: родитель, o: ключ порядка, <поле>: JSON}` |
| `doc` | поле документа (образцы, стили, монтажные области…) | JSON |
| `images` | ключ изображения | `{mime, bytes, proxy?}` |

- **Гранулярность — поле объекта.** `kind` (геометрия), `appearance` (заливка и обводка), `name`,
  `opacity` и прочие поля хранятся отдельно. Если один человек перекрашивает объект, а другой его
  двигает, применятся обе правки.
- **Порядок слоёв задаётся дробными ключами** (`order.rs`), а не общим массивом. При
  перемещении меняется ключ только у перемещённого объекта, и одновременные перестановки не дают
  дублей или потерь.
- **Свои правки → CRDT.** Новый документ сравнивается с последним синхронизированным. Для
  неизменённого поддерева достаточно сравнить указатели (`Arc::ptr_eq`), поэтому стоимость
  пропорциональна размеру правки, а не документа.
- **Чужие правки → документ.** Наблюдатели CRDT собирают затронутые объекты, и пересобираются
  только их поддеревья. Нетронутые поддеревья переиспользуются как есть, так что рендерер и
  кэши их не пересчитывают.
- **Ремонт дерева.** Если объект остался без родителя (родителя удалили одновременно с
  добавлением ребёнка), родитель перестал быть контейнером или встречные переносы образовали цикл,
  объект попадает в конец первого слоя. Все реплики делают это одинаково, поэтому сходятся.
- **Идентификаторы.** У каждого участника свой диапазон id
  (`Document::set_id_range`, `[slot·2³², (slot+1)·2³²)`, всё ниже 2⁵³). Объекты, созданные
  одновременно на разных машинах, не получат одинаковый id.

### Undo только своих правок

В совместном режиме `edit.undo`/`edit.redo` не восстанавливают снимок документа: снимок
откатил бы и чужие правки. Вместо этого команды ставят запрос в `DocState::shared_history`, а
`Collab::tick` выполняет его через `yrs::UndoManager`, который отслеживает только транзакции
этого участника. Одна команда (или один жест, например перетаскивание) — один шаг.

### Жесты и чужие правки

Пока идёт перетаскивание или набор текста (`DocState::interaction`), свой жест публикуется сразу
и остальные видят его вживую. Чужие правки в это время накапливаются и применяются в момент
окончания жеста. Так жест никогда не конфликтует с удалённой правкой.

### Присутствие

Через Yjs awareness каждый участник сообщает имя, цвет, позицию курсора (в координатах документа),
выделенные объекты и активный инструмент. Состояния без обновлений дольше 30 секунд удаляются,
каждый клиент отправляет heartbeat раз в 15 секунд.

## Сервер

`apps/vectorcraft-collab-server` — ретранслятор протокола Yjs с комнатами и хранением на диске
(`<data>/<room>.ydoc`). Протокол стандартный, поэтому к комнате можно подключить и любой
Yjs-клиент, например бота или веб-виджет для просмотра.

```sh
cargo run --release -p vectorcraft-collab-server -- --port 1234 --data ./collab-data
# вместе с веб-версией (после `trunk build --release` в apps/vectorcraft-web):
cargo run --release -p vectorcraft-collab-server -- --static dist/web
```

Docker (веб-приложение и сервер в одном образе):

```sh
docker compose -f packaging/collab/docker-compose.yml up -d --build
# открыть http://<сервер>:1234/?room=poster у каждого участника
```

## Тесты

- `cargo test -p vectorcraft-collab`: сходимость одновременных правок, undo только своих
  правок, встречные переносы, порядок, документ и картинки, протокол, мусорные входные данные,
  property-based fuzz сходимости трёх реплик со случайной доставкой.
- `cargo test -p vectorcraft-engine tests_collab`: две настоящие сессии движка с реальными
  командами через ретранслятор.
- `cargo test -p vectorcraft-collab-server`: настоящий сервер, WebSocket-клиенты, хранение.

## Что дальше

- Права доступа: токены комнат, роли «редактор / наблюдатель» (сообщение `Auth` в протоколе
  уже предусмотрено).
- Комментарии на холсте, история версий (снимки состояния Yjs), «следовать за участником».
- Тонкая синхронизация текста внутри текстового объекта (сейчас текстовый объект — одно поле,
  при одновременном наборе в одном объекте выигрывает последний).
- Живое применение чужих правок и во время своего жеста (сейчас откладываются до его конца).
